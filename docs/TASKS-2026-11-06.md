## 0. 判断与边界

**要解决的四个问题**（按 akiralereal 的启发排序）：

1. **源管理**最值得借鉴——它是整条数据链的上游，我们现在连"这个源为什么抓不到/解析少了几百条/线路为什么差"都查不清。
2. **抓取与代理**——抓不到（IP 限制）、重试不分错误类型（4xx 也重试）、代理只有全局开关。
3. **EPG**——覆盖缺口只能看一个百分比，未映射清单和源优先级都没有。
4. **管理后台**——功能不少但缺"运营视角"：失败归因、趋势、报障/审计闭环、批量操作。

**硬边界（不重蹈 akiralereal 的架构）**：

**额度现实（本清单的硬约束，详见 [`docs/QUOTA-PLAN-2026-11-06.md`](./QUOTA-PLAN-2026-11-06.md)）**：

- 真正的天花板是 **D1 每日行写入 10 万** 和 **KV 每日写 1000**；自 2026-09-01 起 D1 超限会**直接报错**
  （查询失败，不是降级），KV 超限写入失败。
- 历史峰值出现过 KV 写 882/1000、D1 写 89,015/100,000 的一天（`HANDOFF.md:203`，含清理尖峰）。
- 因此每条任务都要标额度影响；Batch 0 先补 **D1 写入护栏 + Actions 分钟护栏**，再动功能。

| 边界 | 含义 |
| --- | --- |
| Cloudflare only | Worker + Actions + D1/KV/R2；**不引入** Node 常驻服务、Docker、自建数据库 |
| CPU 10ms / 额度 | 重活留在 Actions；Worker 只做鉴权、过滤、拼接、缓存 |
| KV | 1000 写/天、单值 25MB；新增产物必须算写放大 |
| 许可 | akiralereal 是 GPLv3：**只借思路，不复制代码** |
| 单出口 | Actions 在海外，无法代表电信/联通（多地区探测是独立议题，不在本清单） |

### P0-1 频道分片桶数读写不一致（真 bug，优先）

- **证据**：`packages/runner/src/pipeline/publish.ts:312` 用 `bucketOf(shard.id, 8)` → 只写 `state/bucket/0..7.json`；
  `packages/worker/src/lib/catalog.ts:40` 用 `bucketOf(channelId, 16)` 读，`:46-48` 再回退 64 桶。测试
  `packages/runner/test/build.test.ts:125` 也固化了 8。
- **影响**：`hash % 16 ≥ 8` 的频道（约一半）详情页读的是**上一次 16 桶发布留下的旧分片**——新频道永远缺线路，
  老频道线路/测速数据陈旧；一旦旧分片被清理就直接空列表。概览与订阅不受影响（走 `out/catalog.json`）。
- **做法（按额度最优）**：统一到 **8**，不是 16——写侧的 8 桶是 2026 年为省 KV 写做的优化
  （`publish.ts:308-309` 注释写得很清楚："halve the number of writes per publish"），错的是读侧。
  `packages/core/src/util/hash.ts` 导出 `BUCKET_COUNT = 8`，worker 读 8、runner 写 8、测试断言 8；
  保留 64 回退；**不重写 16 桶**，省掉 8 次/发布的 KV 写。若未来频道数增长到单桶接近 24MB，再升 16 并同时改读写两侧。

  **已实现**：`hash.ts` 导出 `BUCKET_COUNT = 8` 并作为 `bucketOf` 默认值；runner 写 8；worker 按 8 → 16 → 64 依次回退（去重），
  只对缺失频道多付读；`build.test.ts` 改用 `BUCKET_COUNT`，新增 `core/test/hash.test.ts`。
- **验收**：取覆盖 `hash%16 = 0..15` 的 20 个频道，`/api/public/channels/:id` 的 lines 数与 catalog 一致；
  发布日志 `buckets.size === 8`；本次修复不增加任何 KV 写。

### P0-4 连续失败 5 次会被静默删源（数据丢失）

- **证据**：`packages/worker/src/db.ts:729-734` —— `failures >= 5` 时直接
  `DELETE FROM sources WHERE id = ?` 并删 `source_stats`，注释写着"Permanently broken sources should not linger"。
- **影响**：源站临时故障（Cloudflare 抖动、换域名、GitHub Actions 出口被拦）就会让整条源从后台**消失**，
  历史信誉、过滤配置、手工笔记全丢；后台看不到"它被删了"，只能发现"怎么少了一个源"。
- **做法**：删除改为 `status='paused'`（保留行、保留线路，可在源列表恢复）；
  只有管理员手动删除才真删。阈值进 settings（默认 5）。
- **已实现**：`db.ts` 改为 `UPDATE sources SET status='paused'`；runner 过滤 `status === 'paused'`；后台源卡片显示
  橙色「已暂停」徽章；开关重新启用时清 `paused` 并把 `consecutive_failures` 归零。未加 `paused_reason` 列。
- **验收**：模拟连续 5 轮失败的源仍在列表里显示 paused 且可"重试恢复"；`source_stats` 不被删。
- **注意**：这是 S3 的前置最小修复，先做这一条就能止血。

## 2. 方向一 · 源管理（最值得借鉴，Batch 1）

对照 akiralereal：**每源独立开关/配置/健康/频道数/错误**、**统一 fetch→normalize→validate 管道**、
**源失效可诊断可降级**。我们现在有：增删改查、URL/内容去重（SHA-256）、预览、过滤（分组/关键词/条数）、
刷新间隔、启停、解析检查、抽样测速（Worker 内 8-24 条）、7 天健康统计、信誉分/档位。
缺的是"源级配置 + 可诊断 + 自动降级"。

### S0 源适配器契约（把"格式 switch"升级成"适配器注册表"）

- **现状**：`packages/core/src/parse/index.ts:10-43` 只有内容嗅探 + switch（m3u/txt/json/hwctc）；
  `collect.ts:97-123` 抓取只有 r2/builtin/url 三支。akiralereal 最值得借鉴的结构就是"每源一个模块，
  带 detect/fetch/parse/validate，独立开关与错误"。
- **做法**：`packages/core/src/source/adapter.ts` 定义 `{ id, detect(text, hints), parse(text), validate(entries) }`，
  内置四个适配器包装现有解析器；`sources.kind` 指向适配器 id，未知回退 `auto`。
  **不**引入动态加载/远程插件（Worker 不支持，也不该支持）。
- **验收**：现有 5 种格式经注册表解析结果与当前完全一致；新增一个"站点 JSON API"型适配器只需加一个文件 + 注册。
- **量**：1.5 人日。**注意**：纯结构项，价值在后续扩展速度，放 Batch 1 尾部，不急。

### S1 源级请求配置（UA / Referer / Cookie / 附加头）

- **现状**：只有 M3U 里逐条的 `#EXTVLCOPT`（`RawEntry.headers`）；抓订阅本身固定 Runner UA
  （`packages/runner/src/pipeline/collect.ts:37`、`packages/worker/src/lib/fetcher.ts:26`），源站一拦就抓不到。
- **做法**：`sources` 加列 `request_headers TEXT`（JSON）+ `fetch_mode TEXT`（`direct|worker`，见 F3）；
  runner `fetchPlaylist` 与 Worker `fetchSourceText` 共用一份头合并逻辑（源级头 > 默认 UA）；后台源编辑 Sheet 加"请求设置"折叠区。
- **验收**：给一个需要 Referer 的源配置后抓取成功、`last_ok_at` 更新；线路级 `#EXTVLCOPT` 仍优先于源级头。
- **量**：1.5 人日。**依赖**：migration + Worker 部署。
- **状态（2026-11-06）**：已完成。migration `packages/worker/migrations/0018_source_request_config.sql`（`request_headers`/`fetch_mode`）；`sanitizeSourceHeaders` 在 `packages/core/src/source/fetch.ts`（白名单键、禁 hop-by-hop、单行 ≤2048、最多 16 个）；Worker 创建/预览/列表/编辑与 runner 抓取都带源级头；源面板「请求设置」折叠区（JSON）+ 抓取方式下拉；`deploy.yml` 增加自动 `d1 migrations apply`。测试 24 文件 115 个通过。

### S2 备用地址链（mirror）

- **现状**：`sources.url` 单地址，主地址 404/超时就整源失效。
- **做法**：`sources.mirror_urls TEXT`（JSON 数组），runner 依次尝试并记录"用第几个地址成功"；任一成功即视为 fetched，
  `last_error` 记完整尝试链。后台源卡片显示"主/备"状态。
- **验收**：主地址造 404、备地址正常时，本轮仍解析出条目且源不降级。
- **量**：1 人日。**依赖**：S1 的配置结构。
- **状态（2026-11-06）**：已完成。migration `packages/worker/migrations/0019_source_mirror_urls.sql`；`normalizeMirrorUrls` 在 `packages/core/src/source/mirrors.ts`（最多 5 个、仅 http(s)、去重）；Worker 创建/编辑/列表/详情返回 `mirrorUrls`；runner `parseMirrorUrls` 按「主 → 备」顺序尝试，主地址 304 直接复用，备用命中写 warn 日志；源面板「请求设置」加备用地址多行输入。测试 25 文件 118 个通过。

### S3 源自动降级与恢复（状态机）

- **现状**：`status` 枚举有 `active|degraded|paused`，`db.ts:736` 在 3 次失败时标 `degraded`，
  5 次直接删源（P0-4）——`paused` 实际从不出现，`consecutive_failures` 只在成功时清零；
  cron 另有一条"7 天没成功标 degraded"（`cron.ts:13`）。没有"隔离后自动观察/恢复"的机制。
- **做法**：P0-4 之后，把 5 次失败落为 `paused`；再补：paused 源每 N 轮做一次探测性抓取（半开），成功即恢复 `active`；
  阈值（3/5/N）与半开间隔进 settings；后台"重试并恢复"按钮。
- **验收**：模拟 404 源 3 轮后 degraded、5 轮后 paused 且不再参与正式采集；源站恢复后下一轮半开探测自动回到 active。
- **量**：1 人日。**依赖**：P0-4。
- **状态（2026-11-06）**：已完成。`applySourceStats` 改用 `sourceDegradeThreshold`（默认 3）/`sourcePauseThreshold`（默认 5）；`runSourceRecoveryWatch` 每 `sourceHalfOpenHours`（默认 6）挑一个暂停源派发 `fetch`（payload.source_id）；runner 按 `SOURCE_ID` 放行暂停源；成功后自动回 `active`；源列表/详情页「重试恢复」调 `POST /api/admin/sources/:id/recover`。

### S4 解析诊断持久化（parse_report）

- **现状**：解析检查（`routes/sources.ts:401`）每次都是临时结果，历史无留存；出问题只能靠复现。
- **做法**：每次抓取/解析把 `{detectedKind, entries, groups(top20), warnings, bytes, at}` 写入 `sources.parse_report`
  （JSON 列）并在源详情展示"这次解析到了什么"；对比上一轮条数，突变（>30%）在源卡片标黄。
- **验收**：源详情能看到最近一次与上一次的条数/警告差异；条数突变可被一眼看到。
- **量**：1 人日。

### S5 源健康面板 2.0（含贡献度与"需处理"排序）

### S7 新源导入与单次复测

- **现状**：`packages/core/src/aggregate/state.ts:26-57` 里线路要连续失败 3 次才 `dead`，且 `dead` 带 14 天 `reviveAt` 自动复活；
  `packages/runner/src/cli.ts:770-782` 会把到期的 `dead` 再拉回探测批次。新源里大量"第一次就不可用"的线路因此反复占用批次。
- **做法**：
  1. `LineEntry` 增 `everAlive?: boolean`、`rejectedAt?: string`；首次探测成功置 `everAlive=true`。
  2. `transition()` 改写：从未可用的线路，失败 1 次 → `suspect`（待复测），失败 ≥2 次 → `dead` 终态（记 `rejectedAt`，清 `reviveAt`）；
     曾可用的线路失败 ≥3 次 → `dead` 终态。
  3. 待复测只复测一次（12 小时后）：成功回 `alive`，失败直接终态。
  4. 新源首轮沿用现有流程：抓取 → 轻量测活 → 探测；成功直接进池，未测得留在待测。
- **验收**：5 条坏线路的新源——首轮进待复测；次轮复测失败全部终态；第三轮探测批次不再出现。同源好线路首轮即可用。
- **量**：1.5 人日。

### S8 已淘汰终态与生命周期

- **现状**：`rejected` 仍是 `probePhaseOrder` 默认值（`packages/core/src/types.ts:385`）和 `TASK_PHASES`
  （`packages/worker/src/routes/admin.ts:596`）的一部分；死线路按 14 天 `reviveAt` 反复探测；后台没有"复活/清理淘汰池"入口。
- **做法**：
  1. 已淘汰 = `dead` 终态，不再进入任何自动探测（`isDueForProbe` 对 `dead` 恒 false）；`probePhaseOrder` 默认改 `pending,quarantine`。
  2. 保留 30 天（`rejectedRetentionDays`），**不设总量上限**；到期由清理任务删除，删除前写墓碑（`line_tombstones`），防止重抓再入。
  3. 手动复活：池页面选中线路，或按订阅源取全部已淘汰线路 → 置回待测并派发 `probe-lines` 直接检测；成功回可用，再失败回终态。
  4. 每月最后一天、Actions 剩余 ≥600 分钟时，批量抽检已淘汰池（≤800 条/次）尝试复活；额度不足跳过。
  5. 迁移：现有 `suspect` 且失败次数 ≥2 的直接终态；现有 `dead` 全部清 `reviveAt`、记 `rejectedAt`（一次性迁移接口）。
- **验收**：迁移后连续 3 轮探测无 `rejected` 批次；手动复活能回可用；清理后墓碑生效、重抓不再入池。
- **状态（2026-11-06）**：后端已实现——
  - `POST /api/admin/pool/migrate-rejected`：一次性迁移，幂等（旧 `suspect` 失败≥2/≥3 改终态、`dead` 补 `rejectedAt`、清旧 `reviveAt`）。
  - `POST /api/admin/pool/revive`：按 `keys` 或 `sourceId` 把已淘汰线路置回待测，并派发前 50 条的 `probe-lines`。
  - `cleanup-rejected` 命令：删除超过 `rejectedRetentionDays` 的已淘汰线路，先写墓碑（`line_tombstones`）再删，重抓不会回池。
  - `revive-batch` 命令 + 月末抽检调度：`monthlyReviveEnabled`、`monthlyReviveMinRemainingMinutes`、`monthlyReviveBatchSize`；Actions 余额不足时 1 小时后再试，失败线路直接回终态。
  - 源面板新增「复活淘汰」按钮（按源）；按线路多选复活走 API `keys`，池页多选按钮待做。
- **量**：1.5 人日。**依赖**：S7。

### S9 定时重抓与线路对比

- **现状**：单源 `refresh_hours`（默认 24）已存在，`packages/runner/src/pipeline/collect.ts:87-95` 会跳过未到间隔的源；
  但调度是全局每 7 天一次（`fetchIntervalDays`），且没有对比报表。
- **做法**：
  1. 抓取时间改多时段可配（`fetchTimes`，如 `06:30,12:30,18:30`），到点检查到期源；源分三档：收藏 12 小时、新增（7 天内）24 小时、普通 72 小时，仍可自定义。

  3. 单源每日新增**不设上限**（按你的决定）。
  4. 每源对比结果（新增/复用/消失/跳过淘汰）写 `state/fetch-report.json`，源面板展示。
- **验收**：重抓后新增线路进待测，已淘汰不被拉回；源面板能看到四个数字；源站故障时不误判"消失"。
- **量**：2 人日。**依赖**：S7。
- **状态（2026-11-06）**：已完成。`effectiveRefreshHours` 抽到 `packages/core/src/refresh.ts`（抓取与调度共用）；`normalize()` 返回对比报告并写 `state/fetch-report.json`；`runFetchWatch` 按 `fetchTimes` 多时段触发、无到期源时记 `idle: no source due`；源面板展示「上次对比」。测试 23 文件 109 个通过。

### F1 抓取重试 + 错误归类

- **现状**：`fetchPlaylist` 单次 45s 超时（`collect.ts:28-71`）；`cli.ts:205-218` 在采集层**已有** 3 次重试

  Worker 侧 `fetcher.ts` 则完全无重试。
- **做法**：失败按「网络/DNS/TLS/HTTP 5xx/HTTP 4xx/Cloudflare challenge/不是播放列表/超时」归类，

- **验收**：对返回 502 的源显示"重试 2 次后失败：HTTP 502"；4xx 不重试；源下轮仍会被采集。

### F2 订阅级代理模式（direct / playlist / full）

- **现状**：只有全局 `relayEnabled` 开关（`settings`），导出 M3U 不写任何中继地址
  （`packages/core/src/export/*` 无 relay），只有 Web 播放器走 `/relay/line/:key`。
- **做法**：订阅表加 `proxy_mode`；`playlist` 只代理播放清单/`#EXT-X-KEY`，媒体分片直连（省流量、兼容性最好）；
  `full` 全部走中继。导出时把线路 URL 换成带订阅 token 的签名中继地址（HMAC 绑定 `token + key + exp`，
  不能只绑线路 key，否则任何人可盗链）；订阅编辑页三选一，默认 `direct`。
- **验收**：同一订阅切换三种模式后导出的 M3U 分别出现 0 / 仅清单 / 全部中继地址；禁用订阅后中继地址立即 401。
- **量**：2.5 人日。**依赖**：relay.ts 已有签名框架；注意 Worker 流量与免费额度。

### F3 抓取侧代拉 + 官方源保底

### F4 编码与解析健壮性

  兼容缺逗号的 `#EXTINF`、CRLF、超长行；解析告警分级（致命/可恢复）。
- **验收**：GBK 播放列表导入后频道名正常；已有单测覆盖 BOM/CRLF/坏行。
- **量**：0.5 人日。

### F5 每源抓取参数（超时/并发/请求间隔）

- **做法**：`sources.fetch_timeout_ms`、`fetch_concurrency`（默认 1），runner 采集按配置执行；后台"高级"区可改。

### F6 中继热路径与配额（F2 的前置）

- **现状**：每个分片请求先 `loadSettings()` 打 D1（`relay.ts:160`），再读**整份** `state/probe.json`
  并按 key 线性查找（`:168`）——单请求 CPU 已逼近 Worker 免费版 10ms 上限；F2 的 full 模式会把这条路径
  放大到"每分片一次"。另外旧 `/relay?u=` 只要带订阅 token 就能代理任意 URL（`:126-152`），等于开放代理；
  转发时也不透传 Cookie/Origin（`:43-46`）。
- **做法**：发布时额外产出一份**紧凑索引** `state/line-index.json`（只含 `key → {url, headers}`，

  旧 `/relay` 收敛为只允许清单文件或直接下线；按 token 的粗粒度限流 + 字节配额（KV 计数需注意 1000 写/天，
  计数用 D1 小行或 KV 单键 + 1 次/秒同键限制要避开）；转发补上 Cookie/Origin。
- **验收**：单分片请求不再解析全量 probe.json；任意 URL 代理返回 403；超配额返回 429；带 Cookie 的线路可播。
- **量**：1.5 人日。**依赖**：无（可先做，F2 之前必须做完）。

## 7. 明确不做（借鉴 akiralereal 时要避开的）

1. Node.js + Docker 常驻服务架构（与 Cloudflare-only 冲突）。
2. **B站/抖音/虎牙/斗鱼**的直播逆向——不是线性电视、DRM/反爬重、对 IPTV 价值低。
   （央视频/咪咕已确认做：见 `docs/PLATFORM-SOURCES-2026-11-06.md`，Batch 2.5；仍不进公开频道列表/公开订阅。）

4. 把平台源放进公开频道列表或公开订阅（版权与额度双重风险）。
5. 直接复制 GPLv3 代码（只借设计）。
6. 自建 Android 播放器（OwnTV 方向另议，不在本清单）。
