# 升级前后对比：这套任务清单能带来什么（2026-11-06）

> 配套文档：[`docs/TASKS-2026-11-06.md`](./TASKS-2026-11-06.md)（24 项 / 5 批次 / 约 28 人日）。
> 本文回答一个问题：**全部做完，和现在比，提升在哪、能提升多少。**
>
> 说明：标注「估算」的数字是从代码行为 + 现有数据推算的（例如分桶按哈希均匀分布），
> 不是线上测量值；§1 给了每个指标的测法，实现前后各测一次即可把「估算」换成「实测」。

## 0. 一句话结论

频道数量和线路总量不会因为这些任务变多（那取决于源站）；提升的是**可用率、可诊断性、可控性**：

- **用户侧**：频道详情/试播从"约一半频道读不到最新线路"变成全部可用；订阅可以选择代理模式；CCTV 有官方保底线路。
- **运营侧**：坏源从"看日志猜"变成"面板上一眼看到原因并可一键重试/恢复"；源不再被静默删除；EPG 缺口从"一个百分比"变成"可绑定的清单"。
- **可靠性**：抓取失败有错误分类与选择性重试；EPG 覆盖率不再是"假的 100%"；报障/审计形成闭环。

## 1. 先立 6 个可测指标（现在 vs 目标）

| # | 指标 | 现在 | 目标 | 怎么测 |
| --- | --- | --- | --- | --- |
| M1 | 频道详情页能读到真实线路的频道占比 | **约 50%（估算）**：分片按 8 桶写、16 桶读，`hash%16≥8` 的频道读到旧分片 | ~100% | 抽 20 个频道覆盖 `hash%16=0..15`，比对 `/api/public/channels/:id` 的 lines 与 `out/catalog.json` |
| M2 | 连续失败源的保留/可恢复率 | 5 连败即删除，**0% 可恢复** | 100% 保留并可恢复 | 造一个 404 源跑 5 轮，看列表是否还在 |
| M3 | 抓取失败的可归因率（有错误类别） | 0%（只有一段错误字符串） | 100% | `/api/admin/insights/failures` 按类分布 |
| M4 | EPG 覆盖率的可信度 | 未知（不校验新鲜度，过期也显示 100%） | 真实值 + stale 标记 | 把 `guide.generatedAt` 回拨 30h 看面板 |
| M5 | 订阅可选的代理模式数 | 0（只有全局开关，导出永远直连） | 3（direct / playlist / full） | 三种模式各导出一份 M3U 断言 |
| M6 | 定位一个坏源所需的人工步骤 | ~5–8 步（翻运行日志、查 D1、手动试跑） | 1 屏（面板可见原因 + 一键重试） | 用同一个坏源做排障计时 |

| 后台运营闭环 | 55 | **85** | A1 事件页、A2 失败归因、A3 编排、A4 规则预览、A5 反馈进信誉 |
| 额度 / 成本效率 | 60 | **65** | E5 产物去重是正收益；F2 全代理是负收益（默认关闭） |

## 3. 分方向对比

### 3.1 源管理（Batch 0 的 P0-4 + Batch 1，约 6 人日）

| 场景 | 现在 | 升级后 |
| --- | --- | --- |
| 源站要求 Referer/UA 才能抓 | 抓不到，只能干瞪眼（抓取头写死） | 源级配置，后台填好即可抓 |
| 主地址失效 | 整源失效，靠下一轮 | 自动尝试备用地址 |
| 连续失败 5 轮 | **源被删除，历史全丢** | 暂停保留，可一键恢复；半开探测自动复活 |
| 想知道"这源解析出了什么" | 每次手动点解析检查，无历史 | 自动留档最近两次，条数突变标黄 |
| 排障 | 翻日志、猜 | 面板：最近错误＋归类＋连续失败＋贡献频道数 |
| 批量维护 | 一个个点 | 多选批量启停/改优先级/加标签 |

**可量化**：坏源恢复率 0% → 100%（M2）；排障步骤 5–8 → 1–2（M6）。
**不可量化但真实**：源站拦截导致的"莫名少一个源"这类问题会消失。

### 3.2 抓取与代理（Batch 2，约 8 人日）

| 场景 | 现在 | 升级后 |
| --- | --- | --- |
| 源返回 4xx | 也重试 3 次，白耗时间与额度 | 不重试，直接归类记录 |
| 源返回 5xx/超时 | 同样无差别重试 | 选择性退避重试，结果分类 |
| 需要代理才能播的用户 | 只有全局开关，导出永远是直连 | 订阅三选一：直连 / 清单代理 / 全代理 |
| CCTV 官方源 | 默认关闭（Actions 出口被 CNTV 拦，线路会被判死） | Worker 代拉 + 官方线路不判死，作为保底导出 |
| GBK/BIG5 源 | 导入即乱码 | 自动识别解码 |
| 某源抓取慢 | 全体共用 45s 超时 | 每源可配超时/并发 |

**可量化**：订阅代理模式 0 → 3（M5）；CCTV 频道保底线路 0 → ≥18 条（按官方源清单，估算）。
**代价**：全代理会吃 Worker 流量，所以默认关闭、按订阅显式开启；中继热路径必须先做（F6），否则免费版 CPU 撑不住。

### 3.3 EPG（Batch 3，约 6.5 人日）

| 场景 | 现在 | 升级后 |
| --- | --- | --- |
| 覆盖率 | 只数"有没有节目数组"，过期数据也显示 100% | 校验新鲜度，过期显示 stale；给出按源分布 |
| EPG 里对不上的台名 | 直接造 `x-` 噪声频道，写进 D1 | 落"未映射清单"，可反向绑定，`x-` 可清 |
| XMLTV 全挂 | CCTV 可能没节目 | 官方节目表回退兜底 |
| 多源冲突 | 数组顺序 first-wins + CNTV 硬优先 | 源优先级/权重可配，按频道粒度替换 |
| 20 个订阅的 EPG 体积 | 各生成一份相似 XML | 按频道集哈希共享，只截断不重算 |

**可量化**：未映射清单 0 → 全量（M4 的配套能力）；订阅 EPG 体积估算降 30–50%（按订阅频道集重叠度，估算）。
**上限**：覆盖率能提到多少取决于官方源是否稳定（E3 有反爬风险），任务保证的是"能看见真实缺口并处理"。

### 3.4 管理后台（Batch 4，约 6 人日）

| 场景 | 现在 | 升级后 |
| --- | --- | --- |
| 用户报障 | 有接口，后台没页面 | 事件页：状态流转、转探测、关联频道 |
| 改过什么 | `audit` 只写不读 | 审计页可分页/筛选/看详情 |
| 最近失败最多的是什么 | 逐条看 | TopN 聚合 + 按源/阶段分布 |
| 频道顺序 | DB 有 `sort` 列但 UI 不写 | 拖拽排序 + 批量启停/改名 |
| 规则改完会怎样 | 保存后才知道 | 保存前预览命中数 |
| 反馈与信誉 | 完全不联动 | 有效报障折算进信誉惩罚项 |

**可量化**：后台"能回答的问题"从「有没有报障/改了什么」= 0 个页面 → 2 个页面；规则调参从"试错"变成"先看预览"。

## 4. 用户真正能感知的变化

1. **详情页/试播**：约一半频道现在读到的是旧分片（新频道甚至没有线路），修完后全部与发布目录一致（M1）。
2. **订阅兼容性**：被网络拦截的场景可以选择代理模式，而不是只能等。
3. **CCTV 保底**：官方线路作为兜底出现，不再因为 Actions 出口被拦而全部判死。
4. **频道顺序**：可以按自己的偏好编排（后台拖拽 → 导出顺序一致）。

> 注意：**频道数、线路总数不会因为这份清单明显增长**。数据量由源站决定；这份清单提升的是"已有线路的可用率与可维护性"。

## 6. 诚实边界：这份清单**不**解决什么

1. **不增加频道/线路总量**——那要靠更多源与多地区探测，不在本清单。
2. **不解决源站的法律/封禁风险**——只做可诊断与可降级，不做平台逆向。
3. **不保证抓取成功率上限**——源站封 Actions 出口时，除 Worker 代拉外没有银弹。
4. **EPG 覆盖率提升幅度不确定**——官方源回退受反爬影响，任务保证的是"缺口可见可处理"。
5. **多地区探测（江苏电信 vs 联通）仍是独立议题**——需要 self-hosted runner 矩阵。

## 7. 建议的验收方式

1. 实现 Batch 0 后立刻测 **M1/M2**（当天可测，不依赖采集轮次）。
2. Batch 1 完成后按 M6 做一次真实排障计时（找一个月内失败过的源）。
3. Batch 2 完成后测 **M5**，并用真实播放器验证三种模式。
4. Batch 3 完成后按 **M4** 回拨时间验证 stale 展示，再跑一次真实刷新。
5. 全部完成后做一次"删除一个源→恢复→再删除"的完整演练，确认没有静默丢失。
